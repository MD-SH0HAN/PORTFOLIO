LEVEL 01 / CORE ENGINEERING FOUNDATIONS

Understand the substrate before the platform.

Reliable automation depends on knowing what the machine is doing, how packets move, how software is changed, and how to reason about failure. These foundations apply across Linux servers, containers, cloud services, and Kubernetes.

01.01SYSTEMS

Linux & operating systems

Linux exposes processes, files, devices, users, permissions, namespaces, and services through stable interfaces. An engineer should understand the process lifecycle, signals, memory pressure, filesystems, package managers, systemd, journald, and SSH.

  • Inspect: ps, top, free, df, lsof
  • Operate: systemctl, journalctl, chmod, chown
  • Diagnose resource exhaustion before restarting a service.
ProcessessystemdPermissionsFilesystems
01.02NETWORKING

Networking fundamentals

Services communicate through layered protocols. Understand IPv4/IPv6, CIDR, subnetting, routing, ports, TCP handshakes, UDP, DNS resolution, HTTP semantics, TLS negotiation, firewalls, NAT, and network namespaces.

  • Inspect sockets with ss -tulpn and routes with ip route.
  • Trace resolution with dig; test paths with curl.
  • Separate name-resolution, transport, TLS, and application failures.
TCP/IPDNSHTTP(S)CIDR
01.03COMPUTER SYSTEMS

Architecture & resource behaviour

CPU scheduling, memory allocation, storage I/O, caches, concurrency, virtualization, and kernel boundaries explain application performance and isolation. Capacity is constrained by the slowest or most saturated dependency.

  • Distinguish CPU utilization from load and runnable queue pressure.
  • Reason about memory limits, page cache, disk latency, and I/O wait.
  • Understand VMs, hypervisors, namespaces, and cgroups.
CPU / MemoryI/OVirtualizationConcurrency
01.04AUTOMATION

Shell scripting & programming

Bash is useful for composing command-line tools and operating system tasks; Python is useful for structured automation, APIs, tests, and data transformation. Scripts should fail clearly and be safe to rerun.

  • Quote variables, validate inputs, check exit codes, and use traps.
  • For Bash, consider set -Eeuo pipefail with deliberate error handling.
  • Use Python virtual environments, typed interfaces, tests, and structured logs.
BashPythonJSON / YAMLTesting
01.05CHANGE CONTROL

Git, versioning & SDLC

Git records source history and supports collaborative change through branches, commits, pull requests, reviews, tags, and release notes. The software lifecycle connects requirements, design, implementation, verification, release, operation, and feedback.

  • Keep commits small and reviewable; protect important branches.
  • Use CI checks to make quality expectations repeatable.
  • Version application code, infrastructure, and deployment intent together where appropriate.
GitPull requestsSemantic versioningSDLC
01.06ENGINEERING

Software & API fundamentals

Understand processes, configuration, environment variables, dependency management, HTTP methods and status codes, REST conventions, authentication, idempotency, timeouts, retries, and contract testing.

  • Separate liveness (process alive) from readiness (safe to receive traffic).
  • Design bounded retries with backoff and jitter; avoid retry amplification.
  • Keep configuration out of source and validate contracts at boundaries.
HTTPRESTConfigurationIdempotency

02.01CONTAINERS

Docker & containerization

A container packages a process with its user-space dependencies while sharing the host kernel. Images are layered, content-addressed artifacts; containers add runtime isolation and resource controls.

  • Understand Dockerfile layers, build context, cache, registries, volumes, and networks.
  • Use multi-stage builds, minimal bases, non-root users, read-only filesystems, and pinned versions.
  • Use Compose for local multi-service development—not as a substitute for production orchestration.
Docker EngineBuildKitComposeOCI images
02.02ORCHESTRATION

Kubernetes fundamentals

Kubernetes reconciles declared desired state. Deployments manage ReplicaSets and Pods; Services provide stable discovery; probes, resource requests, limits, and rollout controls shape runtime behaviour.

  • Know Pods, Deployments, Services, ConfigMaps, Secrets, Namespaces, and Ingress/Gateway.
  • Separate startup, liveness, and readiness probe semantics.
  • Use requests for scheduling and limits as enforced resource ceilings.
kubectlDeploymentsServicesProbes
02.03INFRASTRUCTURE AS CODE

Terraform & provisioning

Terraform models infrastructure declaratively. Providers translate configuration into API operations; state maps resource addresses to remote objects and enables planning, dependency ordering, and drift detection.

  • Use modules, typed variables, outputs, provider constraints, and reviewable plans.
  • Protect remote state with access control, encryption, and locking.
  • Never commit state, credentials, or environment-specific secrets.
TerraformProvidersStatePlan / Apply
02.04CONFIGURATION

Ansible & configuration management

Ansible uses an inventory and declarative playbooks to converge hosts toward a desired configuration over SSH or managed connections. Idempotent modules reduce drift and make repeat runs predictable.

  • Structure roles, inventories, variables, handlers, and templates.
  • Use Vault or an external secret manager for sensitive values.
  • Limit blast radius with groups, tags, check mode, and staged rollout.
AnsibleRolesInventoryIdempotency
02.05CI PLATFORMS

Pipeline platforms

CI runners execute jobs in isolated environments, pass artifacts between stages, and expose status checks to source control. Workflow permissions and runner trust boundaries are part of the threat model.

  • Jenkins: controller/agent model, plugins, credentials, shared libraries.
  • GitHub Actions: events, jobs, reusable workflows, environments, OIDC.
  • GitLab CI: stages, jobs, runners, artifacts, environments, rules.
JenkinsGitHub ActionsGitLab CI
02.06CLOUD

Cloud computing

Cloud platforms expose on-demand compute, network, storage, identity, and managed services. Select services by workload needs, failure domains, data residency, operational burden, and cost—not brand preference.

  • AWS: VPC, IAM, EC2, S3, ECR, EKS, RDS, CloudWatch.
  • Azure: VNets, Entra ID, VMs, Blob Storage, ACR, AKS, Monitor.
  • GCP: VPC, IAM, Compute Engine, Cloud Storage, Artifact Registry, GKE, Cloud Operations.
AWSAzureGCPShared responsibility
02.07ARTIFACTS

Artifact & package management

Registries store immutable build outputs and package metadata so releases can be traced, scanned, retained, and promoted consistently. Separate mutable labels from content identity.

  • OCI registries: ECR, GHCR, Docker Hub, ACR, Artifact Registry.
  • Package repositories: npm, PyPI, Maven, NuGet, OS package mirrors.
  • Prefer digest pinning, retention policies, provenance, and SBOMs.
OCIRegistrySBOMDigest
02.08RELEASES

Deployment & release management

Deployment changes runtime state; release management controls when and to whom a version is exposed. Separate build, deploy, and release decisions to reduce risk.

  • Rolling updates trade speed for capacity headroom; blue/green swaps environments.
  • Canary releases increase exposure gradually using health and business signals.
  • Feature flags decouple code deployment from user-visible activation.
RollingBlue/greenCanaryRollback
02.09DELIVERY DESIGN

Infrastructure lifecycle

Infrastructure changes need a controlled lifecycle: request, design, validate, plan, approve, apply, verify, observe, and retire. Environment promotion should preserve traceability.

  • Review policy and cost impact before provisioning.
  • Separate environment state and access; use short-lived credentials.
  • Define ownership, drift detection, teardown, and recovery before rollout.
Change controlPolicyEnvironment promotion

LEVEL 03 / ADVANCED DEVOPS & PLATFORM ENGINEERING

Operate platforms as products and control loops.

Advanced DevOps expands beyond individual pipelines into cluster lifecycle, declarative operations, developer experience, architecture boundaries, and failure-domain design.

03.01KUBERNETES / ADVANCED

Cluster architecture & workload operations

The control plane stores and reconciles cluster state; worker nodes run workloads. The scheduler chooses placement using resource requests and constraints, while controllers continuously compare observed and desired state.

  • Control plane: API server, etcd, scheduler, controller manager.
  • Node: kubelet, container runtime, CNI networking, CSI storage.
  • Scheduling: affinity, anti-affinity, taints/tolerations, topology spread, priority.
  • Operations: HPA, PDB, rollout strategy, autoscaling, admission policy.
etcdSchedulerCNI / CSIHPA / PDB
03.02PACKAGE MANAGEMENT

Helm & Kustomize

Helm templates Kubernetes resources using chart metadata and values; Kustomize composes and patches base manifests into environment overlays. Both should produce inspectable, version-controlled output.

  • Validate charts with helm lint and inspect with helm template.
  • Render overlays with kubectl kustomize before applying.
  • Keep secret material out of plain values and generated manifests.
HelmValues schemaKustomizeOverlays
03.03GITOPS

Argo CD, Flux & reconciliation

GitOps treats version control as the desired-state source. A controller compares the repository with the cluster, reports drift, and optionally reconciles differences using an explicit sync policy.

  • Separate application source from environment configuration and promotion.
  • Use pruning and self-heal intentionally; understand deletion blast radius.
  • Pin image digests and protect the repository path that controls production.
Argo CDFlux CDDrift detectionReconcile
03.04PLATFORM ENGINEERING

Internal developer platforms

A platform provides paved roads for common developer workflows while preserving autonomy and guardrails. A service catalog models ownership and dependencies; templates create consistent starting points.

  • Backstage: software catalog, templates/Scaffolder, documentation, plugins.
  • Golden paths include repository skeletons, CI, security defaults, and service metadata.
  • Measure adoption and friction; avoid building a portal that adds process without reducing toil.
BackstageService catalogScaffolderGolden paths
03.05CLOUD-NATIVE DESIGN

Microservices & service mesh

Microservices split a system around bounded responsibilities but introduce network failure, distributed data, version compatibility, and operational overhead. A service mesh can centralize service-to-service identity, policy, and telemetry.

  • Understand timeouts, retries, circuit breakers, bulkheads, and back-pressure.
  • Use mTLS and workload identity where the trust model requires it.
  • Adopt a mesh only when its operational cost solves a real cross-cutting need.
MicroservicesIstioLinkerdmTLS
03.06RESILIENCE

High availability, scaling & disaster recovery

Availability comes from reducing correlated failure and recovering predictably—not simply adding replicas. Design across zones, dependencies, control planes, data stores, and operational ownership.

  • Distinguish horizontal/vertical scaling and reactive/proactive capacity.
  • Define RTO and RPO; test backup restoration and regional recovery.
  • Use redundancy, health-aware routing, graceful degradation, and game days.
HARTO / RPOBackupFailover
03.07COMPUTE MODELS

Serverless & managed services

Serverless services abstract host management and scale around events or requests. They shift rather than remove operational responsibilities: identity, concurrency, cold starts, quotas, retries, observability, and vendor limits remain.

  • Understand functions, event sources, queues, API gateways, and managed databases.
  • Model timeout, retry, dead-letter, idempotency, and duplicate delivery behaviour.
  • Evaluate lock-in, portability, pricing dimensions, and service quotas.
FaaSEventsManaged servicesQuotas
03.08HYBRID / MULTI-CLOUD

Multi-cloud & hybrid infrastructure

Multi-cloud and hybrid designs introduce identity federation, network connectivity, data movement, policy consistency, observability, and duplicated platform operations. Portability should be driven by a concrete requirement.

  • Map shared responsibility and control boundaries per provider.
  • Standardize workload interfaces without hiding important provider differences.
  • Plan egress cost, latency, data gravity, failover, and operational skills.
Hybrid cloudFederationPortabilityData gravity

CONTROL PLANE

API server · etcd · scheduler · controllers

The API server exposes the control interface; etcd stores cluster state; the scheduler assigns Pods to nodes; controllers continuously reconcile observed state toward declared state.

PLATFORM ENGINEERING / GITOPS

Make the paved road the easiest road.

Platform engineering treats the developer experience as a product. Internal developer platforms package common workflows, guardrails, and self-service capabilities so teams can deliver without repeatedly solving the same infrastructure problems.

01 / SELF-SERVICE

Internal Developer Platforms

Service catalogs, templates, environment provisioning, documentation, ownership metadata, and access workflows reduce repetitive setup while keeping responsibilities clear.

  • Track onboarding time and developer feedback.
  • Expose supported operations through clear APIs and permissions.
  • Keep the platform optional where team needs genuinely differ.
02 / GOLDEN PATHS

Opinionated, supported defaults

A golden path can provide a repository template, CI pipeline, container build, security checks, deployment conventions, service metadata, and an observable runtime baseline.

  • Make defaults secure and maintainable.
  • Version templates and publish migration guidance.
  • Measure adoption, lead time, reliability, and friction.
03 / GITOPS

Reconcile declared state

GitOps stores desired configuration in version control and uses a controller such as Argo CD or Flux to compare and reconcile cluster state. Git becomes a reviewable source of deployment intent.

  • Separate application source from environment configuration where useful.
  • Use protected branches, signed artifacts, and scoped controller permissions.
  • Observe sync health, drift, and rollback paths.
LEVEL 04 / OBSERVABILITY, RELIABILITY & SECURITY

Make production behaviour visible and defensible.

Operations depends on meaningful telemetry, service-level objectives, disciplined incident response, and controls that reduce the likelihood and impact of compromise.

04.01METRICS

Prometheus & alerting

Prometheus scrapes instrumented endpoints, stores time-series data, and evaluates PromQL queries and alert rules. Labels must be bounded: unbounded values such as raw URLs, user IDs, or request IDs create cardinality explosions.

  • Instrument counters, gauges, histograms, and summaries appropriately.
  • Use recording rules for repeated expensive queries and alert on symptoms.
  • Pair alerts with an owner, severity, runbook, and actionable threshold.
PromQLExportersAlert rulesCardinality
04.02VISUALIZATION

Grafana & operational dashboards

Grafana queries data sources and assembles panels, variables, annotations, and alert views. Dashboards should answer operational questions and expose trends, not become a wall of unrelated charts.

  • Show request rate, error ratio, latency percentiles, and saturation.
  • Include deployment markers and links to logs or traces.
  • Version-control dashboard definitions and datasource provisioning.
GrafanaDashboardsAnnotationsProvisioning
04.03TRACING / LOGGING

OpenTelemetry & distributed tracing

Distributed traces connect spans across service boundaries using propagated context. Structured logs add event detail; trace and span identifiers help correlate an individual request across components.

  • Use sampling intentionally and avoid putting sensitive data in span attributes.
  • Control log volume, retention, parsing, and access boundaries.
  • Use the Collector for batching, processing, filtering, and export pipelines.
OTel SDKCollectorTrace contextStructured logs
04.04SRE

SLIs, SLOs, SLAs & error budgets

An SLI is a measured indicator of service behaviour; an SLO is an internal target over a window; an SLA is an external agreement with consequences. Error budgets quantify the unreliability allowed by an SLO.

  • Define eligible events and good-event criteria before calculating availability.
  • Use latency percentiles for tail behaviour; averages can hide bad experiences.
  • Use budget policy to balance release velocity with reliability investment.
SLISLOSLAError budget
04.05OPERATIONS

Incident management & RCA

Incident response is a coordinated workflow: detect, declare, assign roles, mitigate, communicate, recover, and learn. Root cause analysis should explain contributing conditions and system weaknesses rather than assign blame.

  • Maintain runbooks, escalation paths, status updates, and incident timelines.
  • Distinguish mitigation from permanent remediation.
  • Turn post-incident actions into owned, prioritized engineering changes.
On-callRunbooksRCAPostmortem
04.06DEVSECOPS

Security across the delivery lifecycle

DevSecOps embeds risk checks into design, source, build, release, and runtime. Automation supports—not replaces—threat modelling, ownership, patching, and human review.

  • SAST, SCA, secret scanning, IaC scanning, container scanning, and DAST.
  • Generate SBOMs; sign artifacts and verify provenance where supported.
  • Set severity policy and exception expiry; scan base images and dependencies.
SAST / SCATrivySBOMSupply chain
04.07IDENTITY

IAM, secrets & access control

Identity defines who or what can perform an action on which resource. Least privilege, short-lived credentials, workload identity, and auditable authorization reduce credential exposure and lateral movement.

  • Use role-based or attribute-based policies and scope trust relationships narrowly.
  • Prefer OIDC federation and managed identities to long-lived CI keys.
  • Use a secret manager, rotation, access logging, and avoid secret leakage in logs.
IAMRBACOIDCSecrets
04.08NETWORK / DATA SECURITY

Network security, backup & recovery

Security boundaries include network segmentation, TLS, firewall policy, private endpoints, encryption at rest, and controlled egress. Backups are valuable only when restoration has been tested.

  • Use default-deny policies where practical and verify CNI/firewall enforcement.
  • Manage certificates, keys, rotation, and trust roots deliberately.
  • Encrypt backups, isolate credentials, define RPO/RTO, and run restore drills.
NetworkPolicyTLSKMSRecovery drills
04.09GOVERNANCE

Compliance & policy

Governance translates regulatory, contractual, and organizational requirements into controls with clear ownership and evidence. Frameworks such as CIS Benchmarks, NIST guidance, and ISO 27001 can inform control design.

  • Use policy-as-code to check configuration before deployment.
  • Maintain asset inventory, audit trails, retention, and exception records.
  • Match controls to actual obligations; avoid claiming certification without independent assessment.
CISNISTPolicy as codeAuditability

CLOUD SECURITY / DEVSECOPS

Build security into the delivery path.

Security controls work best when they are layered into identity, network boundaries, source, build, artifact, infrastructure, and runtime workflows. A scanner result is one signal—not proof of security or compliance.

IDENTITY & ACCESS

Least privilege by default

Prefer federation and short-lived credentials; scope IAM roles, service accounts, and Kubernetes RBAC to the minimum required actions and resources.

NETWORK & DATA

Constrain and encrypt

Segment workloads, restrict ingress and egress, encrypt data in transit and at rest, rotate certificates, and control administrative paths.

SECRETS & SUPPLY CHAIN

Protect sensitive inputs

Use a secrets manager or external secret integration, detect accidental leaks, pin dependencies, scan images, generate SBOMs, and verify signatures where supported.

POLICY & COMPLIANCE

Make controls verifiable

Use policy as code, audit logs, vulnerability triage, backup controls, documented exceptions, and evidence collection. Compliance requires context beyond a tool badge.

LEVEL 05 / SUPPORTING ENGINEERING DISCIPLINES

The dependencies behind the delivery platform.

Infrastructure is a connected system. Engineers need enough depth in data, traffic management, interfaces, storage, documentation, and economics to design and operate the whole service path.

05.01INTERFACES

APIs & service contracts

APIs define boundaries between services and clients. Contracts include schemas, status codes, auth, pagination, rate limits, versioning, timeouts, and backward-compatible change practices.

  • Document OpenAPI contracts and validate requests/responses.
  • Use health endpoints with distinct liveness and readiness meaning.
  • Design idempotency keys for retried write operations where appropriate.
RESTOpenAPIgRPCRate limiting
05.02DATA

Databases & caching

Data services introduce consistency, durability, availability, query performance, replication, and backup concerns. Application reliability is often bounded by a database or cache dependency.

  • Relational: transactions, indexes, isolation, connection pools, migrations.
  • NoSQL: access patterns, partitioning, consistency, TTL, replication.
  • Cache: invalidation, stampede control, eviction, and stale-data tolerance.
PostgreSQLMySQLRedisBackups
05.03TRAFFIC

Reverse proxies & load balancers

A reverse proxy terminates or forwards client connections, applies routing and policy, and can provide TLS termination, caching, compression, and request limits. Load balancers distribute traffic according to health and routing rules.

  • Understand L4 vs L7 load balancing and health-check behaviour.
  • Configure forwarded headers, trusted proxy ranges, timeouts, and body limits.
  • Plan graceful draining and connection reuse during rollout.
NGINXHAProxyEnvoyIngress / Gateway
05.04NETWORK SERVICES

DNS, TLS & certificates

DNS maps names to records through recursive and authoritative resolution; TLS authenticates peers and encrypts transport. Certificate lifecycle and DNS changes are operational dependencies, not one-time setup tasks.

  • Know A/AAAA, CNAME, TXT, MX, TTL, delegation, and split-horizon DNS.
  • Understand certificate chains, SANs, expiry, renewal, and private keys.
  • Use automated renewal with monitoring and a tested failure path.
DNSTLS 1.2/1.3ACMEPKI
05.05WEB / EDGE

Web servers & application runtime

Web servers handle static content, connection management, reverse proxying, and TLS. Application servers execute service logic and should expose predictable process, health, and shutdown behaviour.

  • Separate edge concerns from application responsibilities.
  • Set graceful shutdown, request timeouts, concurrency limits, and log format.
  • Test configuration before reload and keep a known-good rollback path.
NGINXApacheGunicornGraceful shutdown
05.06STORAGE

Storage systems & persistence

Object, block, and file storage have different access patterns and consistency/performance characteristics. Containers are ephemeral by default; persistent state needs explicit lifecycle, backup, encryption, and recovery design.

  • Object storage for durable blobs; block volumes for mounted disks; file storage for shared filesystem access.
  • Understand CSI, snapshots, retention, lifecycle rules, and encryption.
  • Test data restoration and application consistency, not just backup job completion.
S3 / BlobVolumesCSISnapshots
05.07ASYNC SYSTEMS

Message queues & event systems

Queues decouple producers and consumers, buffer bursts, and enable asynchronous work. They require explicit delivery semantics, ordering expectations, dead-letter handling, and consumer idempotency.

  • Distinguish at-most-once, at-least-once, and exactly-once claims.
  • Use back-pressure, bounded retries, dead-letter queues, and replay controls.
  • Monitor lag, age of oldest message, throughput, and poison messages.
RabbitMQKafkaSQSDLQ
05.08COLLABORATION

Documentation & engineering practice

Documentation is part of the operational interface: architecture decisions, ownership, setup, runbooks, service catalog entries, and change records make systems understandable to the next operator.

  • Maintain concise READMEs, ADRs, diagrams, runbooks, and onboarding guides.
  • Use code review, small pull requests, clear issue triage, and shared ownership.
  • Keep docs close to code and review them as part of change.
ADRsRunbooksCode reviewOwnership
05.09ECONOMICS

Cost optimization & FinOps

FinOps brings engineering, finance, and business teams together around informed cloud spending. Cost optimization balances utilization, performance, resilience, and organizational priorities.

  • Tag ownership; allocate shared costs; set budgets and anomaly alerts.
  • Review idle resources, right-sizing, autoscaling, storage lifecycle, and egress.
  • Include cost estimates in infrastructure plans and evaluate recurring costs before enablement.
FinOpsBudgetsRight-sizingCost allocation

REFERENCE PATTERNS
REF 01 / OBSERVABILITYLOCAL-FIRST MODEL

API → Prometheus → Grafana

A compact service can expose health contracts and metrics, while a collector scrapes time-series data and a dashboard visualizes operational behaviour. Docker Compose is useful for a local multi-service learning topology.

Python API/healthz · /readyz · /metrics→Prometheusscrape · store · alert→Grafanaquery · dashboard
Service contract

/healthz checks process liveness; /readyz can return 503 while a dependency or startup condition prevents traffic; /metrics exposes Prometheus-formatted metrics.

Instrumentation

Request counters and latency histograms should use bounded labels. Scrape traffic should be excluded from application request metrics to avoid distorting service traffic signals.

Operational boundary

Local Compose networking, in-memory metrics, and a provisioned dashboard are useful for learning. Production needs durable telemetry, secured ingress, authentication, alert routing, retention, and a defined SLO policy.

REF 02 / CLOUD FOUNDATIONAWS + TERRAFORM MODEL

Two-zone network & private workloads

A common cloud foundation separates public entry points from private application subnets across availability zones, then applies identity, routing, registry, and cost controls through infrastructure as code.

VPC / CIDR
AZ APublic subnet · edgePrivate subnet · workloads
AZ BPublic subnet · edgePrivate subnet · workloads
IGW at the edge · optional NAT egress · registry / ECR · optional managed cluster / EKS
Terraform lifecycle

Declare VPC, subnets, route tables, security boundaries, registry, and optional cluster resources. Run format, validate, plan, and review before apply; retain protected remote state in a real team workflow.

Safer defaults

Keep expensive resources opt-in. The source pattern used NAT and EKS disabled by default, immutable ECR tags, scan-on-push, and a restricted cluster API CIDR when enabled.

Trade-offs

A single NAT gateway is a cost-conscious learning compromise, not zone-resilient egress. Production designs need a deliberate multi-AZ, private endpoint, IAM, logging, KMS, and state-backend strategy.

REF 03 / KUBERNETES WORKLOADHARDENED BASELINE

Workload contract & traffic safety

A Kubernetes workload definition describes the desired replica count, update strategy, health, capacity, identity, and network exposure. A manifest being accepted does not prove that every runtime control is enforced.

Deploymentreplicas · rollout→Pod healthstartup · live · ready→Serviceready endpoints→HPAscale signal
Workload controls

Use resource requests/limits, non-root UID/GID, read-only root filesystem, no privilege escalation, dropped capabilities, seccomp, and a dedicated ServiceAccount.

Availability controls

Rolling update settings, topology spread, HPA, and PodDisruptionBudget address different failure modes. HPA needs a working Metrics API; PDB mainly constrains voluntary disruption.

Network boundary

NetworkPolicy only has effect when the CNI enforces it. Start with scoped ingress and egress, then test actual allowed and denied flows in the target cluster.

REF 04 / DELIVERY SUPPLY CHAINCI → REGISTRY → GITOPS

Build once; deploy by immutable identity

A release workflow should turn a reviewed commit into a tested, scanned, traceable artifact, then let a deployment controller reconcile a reviewed desired-state change.

CI workflowtests · Buildx→SecurityTrivy · CycloneDX→GHCRimmutable digest→Argo CDHelm reconcile
CI responsibilities

Run unit and HTTP smoke tests, build with Buildx, generate a CycloneDX SBOM, scan relevant HIGH/CRITICAL vulnerabilities under an explicit policy, and publish the exact digest.

GitOps responsibilities

Argo CD watches declarative source and can automate sync, pruning, and self-heal. Use digest-pinned images and review deletion/pruning scope before enabling automatic reconciliation.

Security boundary

Use minimal workflow permissions, short-lived OIDC credentials where cloud access is needed, protected environments, provenance, and secret isolation. A workflow file is not evidence that a release was deployed.

REF 05 / OPERATING SIGNALSMETRICS + ALERTS

From a measurement to a response

Telemetry becomes operationally useful when a team defines service health, connects alerts to ownership, and can explain what action should follow each signal.

REDRate · Errors · Duration
USEUtilization · Saturation · Errors
GOLDENLatency · Traffic · Errors · Saturation
Alert design

Alert on user-visible symptoms and sustained conditions; add severity, routing, owner, runbook, and an actionable threshold. Avoid paging on every transient fluctuation.

Signal quality

Label cardinality, scrape interval, histogram buckets, sampling, clock skew, retention, and access policy affect observability cost and correctness.

Operational learning

Use sample traces, configuration diffs, and recovery drills to practice diagnosis. Simulations are explicitly illustrative and never presented as live telemetry.

REF 06 / DEVELOPER EXPERIENCESERVICE CATALOG

Catalog entities & golden paths

A Backstage Software Catalog can describe components, APIs, owners, and relationships. A Scaffolder template can generate a repository skeleton with conventions and register the resulting component.

Developer inputname · owner · metadata→Scaffoldertemplate · policy→Repositorycode · tests · CI→Catalogcomponent · API
Golden path

Provide a supported service skeleton, CI workflow, container build, ownership metadata, docs, and secure defaults. Keep the generated template small and maintained.

Integration boundary

Catalog YAML and template source do not constitute a running developer portal. A real Backstage deployment needs integrations, permissions, publication actions, and protected secret handling.

Platform metric

Measure time-to-first-deploy, template adoption, policy compliance, developer satisfaction, and reduction in repetitive setup work.
