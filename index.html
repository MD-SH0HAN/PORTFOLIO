LEVEL 01 / CORE ENGINEERING FOUNDATIONS

Understand the substrate before the platform.

Reliable automation depends on knowing what the machine is doing, how packets move, how software is changed, and how to reason about failure. These foundations apply across Linux servers, containers, cloud services, and Kubernetes.

Start here when a later cloud or Kubernetes symptom is difficult to explain: the operating system and network usually provide the first useful evidence.

01.01SYSTEMS

Linux & operating systems

Linux exposes processes, files, devices, users, permissions, namespaces, and services through stable interfaces. An engineer should understand the process lifecycle, signals, memory pressure, filesystems, package managers, systemd, journald, and SSH.

Operational checks3 applied checks · optional
  • Inspect: ps, top, free, df, lsof
  • Operate: systemctl, journalctl, chmod, chown
  • Diagnose resource exhaustion before restarting a service.

Triage resource pressure before changing service state

Start with the symptom and correlate independent signals: CPU run queue and load, memory pressure and OOM events, filesystem capacity and inode exhaustion, disk latency, open file descriptors, and service logs. A high CPU percentage alone does not identify the process or prove CPU saturation. Capture the failing unit state and recent journal entries before restarting it; a restart can temporarily hide the evidence and may not fix an exhausted dependency.

Verification approach

Compare process-level signals with host-level signals, then inspect the service’s cgroup limits and dependencies. Record the observation, likely constraint, corrective action, and post-change verification.

ProcessessystemdPermissionsFilesystems
01.02NETWORKING

Networking fundamentals

Services communicate through layered protocols. Understand IPv4/IPv6, CIDR, subnetting, routing, ports, TCP handshakes, UDP, DNS resolution, HTTP semantics, TLS negotiation, firewalls, NAT, and network namespaces.

Operational checks3 applied checks · optional
  • Inspect sockets with ss -tulpn and routes with ip route.
  • Trace resolution with dig; test paths with curl.
  • Separate name-resolution, transport, TLS, and application failures.

Diagnose from name resolution to application response

Follow the request path in layers: resolve the name and inspect the returned address; verify routing and TCP reachability; validate the TLS certificate, hostname and SNI; then inspect the HTTP status, headers and application response. A successful DNS lookup does not prove that a TCP connection, TLS handshake, or application request will succeed. Proxies, NAT, security groups, local firewalls and service listeners can fail at different points.

Verification approach

Use targeted checks such as dig, ip route, ss, curl -v and (when needed) openssl s_client. Change one boundary at a time so the test identifies which layer is failing.

TCP/IPDNSHTTP(S)CIDR

01.05CHANGE CONTROL

Git, versioning & SDLC

Git records source history and supports collaborative change through branches, commits, pull requests, reviews, tags, and release notes. The software lifecycle connects requirements, design, implementation, verification, release, operation, and feedback.

Operational checks3 applied checks · optional
  • Keep commits small and reviewable; protect important branches.
  • Use CI checks to make quality expectations repeatable.
  • Version application code, infrastructure, and deployment intent together where appropriate.

Preserve traceability from reviewed change to running release

A branch name is a movable reference; a commit SHA identifies a specific source revision. A reliable delivery record links that revision to the workflow run, test and security results, immutable artifact digest, approval, deployment environment and resulting runtime version. This makes rollback and incident investigation evidence-based instead of relying on a tag or a human-readable release label alone.

Verification approach

For a release, verify the commit identity and artifact digest at each hand-off. Promote the same artifact between environments rather than rebuilding it separately for staging and production.

  • Use multi-stage builds, minimal bases, non-root users, read-only filesystems, and pinned versions.
  • Use Compose for local multi-service development—not as a substitute for production orchestration.
Docker EngineBuildKitComposeOCI images
02.02ORCHESTRATION

Kubernetes fundamentals

Kubernetes reconciles declared desired state. Deployments manage ReplicaSets and Pods; Services provide stable discovery; probes, resource requests, limits, and rollout controls shape runtime behaviour.

Operational checks3 applied checks · optional
  • Know Pods, Deployments, Services, ConfigMaps, Secrets, Namespaces, and Ingress/Gateway.
  • Separate startup, liveness, and readiness probe semantics.
  • Use requests for scheduling and limits as enforced resource ceilings.

Separate scheduling, readiness and restart decisions

Resource requests influence scheduling and capacity accounting; limits constrain resource use at runtime. CPU limit pressure can throttle execution, while exceeding a memory limit can lead to an OOM kill. A startup probe gives slow-starting workloads time to initialize; readiness controls whether a Pod should receive service traffic; liveness determines whether the container should be restarted. A readiness failure alone does not mean the process is dead.

Verification approach

When a Pod is unhealthy, inspect events, scheduling conditions, container state and previous logs before changing probes or raising limits. Check whether the application is actually ready, whether dependencies are reachable, and whether resource settings match observed behaviour.

kubectlDeploymentsServicesProbes
02.03INFRASTRUCTURE AS CODE

Terraform & provisioning

Terraform models infrastructure declaratively. Providers translate configuration into API operations; state maps resource addresses to remote objects and enables planning, dependency ordering, and drift detection.

Operational checks3 applied checks · optional
  • Use modules, typed variables, outputs, provider constraints, and reviewable plans.
  • Protect remote state with access control, encryption, and locking.
  • Never commit state, credentials, or environment-specific secrets.

Treat state and plans as sensitive change-control inputs

Terraform state maps configuration addresses to remote objects and can contain sensitive values. Use an access-controlled remote backend with encryption and a supported locking mechanism; separate state boundaries according to ownership and blast radius. Review plans for replacements, deletes, dependency changes and unexpected drift. A successful plan is not proof that an API change will be harmless at runtime, so destructive or high-impact changes still need human review and a recovery plan.

Verification approach

For controlled automation, create and inspect a saved plan, protect both the plan file and state, apply only the reviewed plan, and verify the resulting resource and service health. Never commit state, plan files or credentials to source control.

TerraformProvidersStatePlan / Apply

02.05CI PLATFORMS

Pipeline platforms

CI runners execute jobs in isolated environments, pass artifacts between stages, and expose status checks to source control. Workflow permissions and runner trust boundaries are part of the threat model.

Operational checks3 applied checks · optional
  • Jenkins: controller/agent model, plugins, credentials, shared libraries.
  • GitHub Actions: events, jobs, reusable workflows, environments, OIDC.
  • GitLab CI: stages, jobs, runners, artifacts, environments, rules.

Secure the runner and preserve artifact identity

A CI job executes with the permissions of its runner and workflow token. Treat pull-request code, third-party actions, build scripts, caches and downloaded dependencies as inputs that can affect the job. Use minimal token permissions, pin trusted workflow dependencies where practical, isolate untrusted workloads, and avoid exposing deployment credentials to jobs that only need to test code. Federated short-lived identity is preferable to a long-lived cloud key stored in CI.

Verification approach

Record the source commit, workflow identity, test results and artifact digest. Scan and attest the artifact that will actually be deployed; promotion should move that artifact, not silently rebuild a different one.

03.01KUBERNETES / ADVANCED

Cluster architecture & workload operations

The control plane stores and reconciles cluster state; worker nodes run workloads. The scheduler chooses placement using resource requests and constraints, while controllers continuously compare observed and desired state.

Operational checks4 applied checks · optional
  • Control plane: API server, etcd, scheduler, controller manager.
  • Node: kubelet, container runtime, CNI networking, CSI storage.
  • Scheduling: affinity, anti-affinity, taints/tolerations, topology spread, priority.
  • Operations: HPA, PDB, rollout strategy, autoscaling, admission policy.

Follow the control loop, not just the Pod status

Kubernetes controllers repeatedly compare observed state with declared desired state and take actions to reduce the difference. A Deployment manages ReplicaSets, which manage Pods; the scheduler places unscheduled Pods using requests and constraints; kubelets and the runtime then act on assigned workloads. A pending Pod, a running-but-unready Pod and a crash-looping container are different failure states and need different evidence.

Verification approach

Trace the object chain from Deployment to ReplicaSet to Pod, inspect events and conditions, and confirm service endpoints before concluding that a rollout is healthy. Desired replica count is not the same as available capacity.

etcdSchedulerCNI / CSIHPA / PDB

03.03GITOPS

Argo CD, Flux & reconciliation

GitOps treats version control as the desired-state source. A controller compares the repository with the cluster, reports drift, and optionally reconciles differences using an explicit sync policy.

Operational checks3 applied checks · optional
  • Separate application source from environment configuration and promotion.
  • Use pruning and self-heal intentionally; understand deletion blast radius.
  • Pin image digests and protect the repository path that controls production.

Make reconciliation policy and deletion behaviour explicit

GitOps controllers compare declared repository state with live cluster state. Depending on sync policy, manual changes may be reported as drift or corrected automatically. Pruning can delete resources removed from the source, while self-heal can overwrite manual edits; both are powerful controls with a real blast radius. The repository path, branch protections, credentials and secret-delivery method therefore form part of the production trust boundary.

Verification approach

Test drift, prune and rollback behaviour in a disposable environment. Prefer a reviewed source change or revert for durable correction, and ensure secrets are encrypted or sourced through an appropriate external secret mechanism rather than committed as plaintext manifests.

03.06RESILIENCE

High availability, scaling & disaster recovery

Availability comes from reducing correlated failure and recovering predictably—not simply adding replicas. Design across zones, dependencies, control planes, data stores, and operational ownership.

Operational checks3 applied checks · optional
  • Distinguish horizontal/vertical scaling and reactive/proactive capacity.
  • Define RTO and RPO; test backup restoration and regional recovery.
  • Use redundancy, health-aware routing, graceful degradation, and game days.

Redundancy, backups and recovery solve different problems

Replicas and multiple availability zones can reduce the impact of some component failures, but they do not replace backups or prove that data can be restored. Replication may copy accidental deletion or corruption. RTO describes the target time to restore service; RPO describes the acceptable data-loss window. Both depend on tested recovery procedures, dependency availability, capacity and people—not only the existence of a backup job.

Verification approach

Run restore exercises and record actual recovery time and recovered data point. Test the failure domains that matter to the service, including identity, DNS, network paths and external dependencies.

HARTO / RPOBackupFailover

LEVEL 04 / OBSERVABILITY, RELIABILITY & SECURITY

Make production behaviour visible and defensible.

04.01METRICS

Prometheus & alerting

Prometheus scrapes instrumented endpoints, stores time-series data, and evaluates PromQL queries and alert rules. Labels must be bounded: unbounded values such as raw URLs, user IDs, or request IDs create cardinality explosions.

Operational checks3 applied checks · optional
  • Instrument counters, gauges, histograms, and summaries appropriately.
  • Use recording rules for repeated expensive queries and alert on symptoms.
  • Pair alerts with an owner, severity, runbook, and actionable threshold.

Keep time-series cardinality bounded and queries meaningful

Prometheus stores a separate time series for each unique label set. Labels such as user IDs, request IDs, session IDs or unrestricted raw URLs can create very high cardinality and increase memory, storage and query cost. Apply rate() to counters before aggregation so resets are handled, and choose histogram buckets that match the latency thresholds the service needs to reason about. Histograms can be aggregated across instances; precomputed summary quantiles generally cannot.

Verification approach

Review label dimensions before instrumentation ships. Alert on user-visible symptoms and actionable conditions, and make every alert point to an owner, runbook and clear next action.

PromQLExportersAlert rulesCardinality
04.02VISUALIZATION

Operational checks3 applied checks · optional

04.04SRE

SLIs, SLOs, SLAs & error budgets

An SLI is a measured indicator of service behaviour; an SLO is an internal target over a window; an SLA is an external agreement with consequences. Error budgets quantify the unreliability allowed by an SLO.

Operational checks3 applied checks · optional
  • Define eligible events and good-event criteria before calculating availability.
  • Use latency percentiles for tail behaviour; averages can hide bad experiences.
  • Use budget policy to balance release velocity with reliability investment.

Define the measurement before selecting the target

An availability SLI needs an explicit eligible-event population and a definition of a good event; otherwise the numerator and denominator can hide failures. A latency SLI should specify the threshold and percentile or good-event ratio being measured. An SLO applies that indicator over a stated window, while the error budget represents the allowed bad events in that window. Averages can conceal tail latency and uneven user impact.

Verification approach

Write down the event filter, good-event condition, measurement window and owner before setting an SLO target. Use burn-rate alerts to detect fast budget consumption, then connect the response policy to release risk and reliability work.

04.07IDENTITY

IAM, secrets & access control

Operational checks3 applied checks · optional
  • Use role-based or attribute-based policies and scope trust relationships narrowly.
  • Prefer OIDC federation and managed identities to long-lived CI keys.
  • Use a secret manager, rotation, access logging, and avoid secret leakage in logs.

Constrain identity at both the principal and trust boundary

A role policy describes what a principal can do; a trust policy or federation rule describes who may assume that role. Both matter. For CI federation, constrain issuer, audience and repository or environment identity claims as narrowly as the provider supports. Keep human access separate from workload identity, scope secrets to their consumers, and log privileged actions. A short-lived token is still dangerous when its permissions or trust conditions are broad.

Verification approach

Review the complete chain: identity source, trust conditions, effective permissions, secret exposure, token lifetime and audit trail. Test both an allowed action and an explicitly denied action.

ADR 01 / TERRAFORMWhen is a plan safe to apply?+

Decision: Review the complete proposed action set, provider changes, replacements, deletions, dependency effects and policy results before authorization. A plan is a preview, not an approval.

Verify: Recalculate the final plan against current remote objects, confirm the intended workspace/backend, inspect any saved plan as sensitive material, and protect state access and locking.

Trade-off: Saved plans support reviewed automation, but plan files can contain sensitive values. Store them only in a controlled, short-lived workflow and never commit them to source control.

ADR 02 / KUBERNETESRunning does not mean ready.+

Decision: Treat startup, liveness and readiness as separate contracts. A process can be running while initialization or a dependency still prevents it from serving traffic.

Verify: Compare Pod conditions and probe events with Service selectors and EndpointSlice readiness. Confirm whether the endpoint should receive traffic before changing a probe threshold.

ARCHITECTURE REVIEW STUDIO / DECISION PRACTICE

Compare the trade-offs before choosing a design.

These are conceptual review exercises for learning. No option is universally correct; the answer depends on workload requirements, team capability, threat model, cost envelope and recovery objectives.

SCENARIO 01 / RUNTIME PLATFORMManaged containers or Kubernetes?+

Choose a managed container service when: the application needs standard container scheduling, the team has limited platform operations capacity, and advanced orchestration features are not required.

Choose Kubernetes when: multiple workloads need a common orchestration API, portability or ecosystem integrations are material, and the team can own cluster lifecycle, policy, upgrades, networking and incident response.

Review before decision: operational staffing, workload count, traffic shape, deployment controls, identity integration, network policy, upgrade ownership, recovery objectives and total cost of ownership.

Failure test: simulate an unavailable node or failed rollout in a disposable environment; observe scheduling/recovery, service health, alerting and rollback. Do not infer resilience from replica count alone.

Decision rule: prefer the least complex platform that satisfies explicit requirements. Kubernetes is a capability choice, not a default badge of maturity.

SCENARIO 02 / RESILIENCEMulti-AZ or multi-region?+

Multi-AZ: usually addresses a narrower availability-zone failure domain with lower replication and coordination complexity than a second region.

Multi-region: may reduce regional outage exposure, but adds data consistency, routing, identity, secrets, observability, failover, and operational coordination work.

Review before decision: service-specific RTO/RPO, synchronous versus asynchronous replication, write authority, split-brain prevention, dependency locality, data residency, recovery testing and regional cost.

Failure test: rehearse a region/zone loss scenario in a controlled environment; verify that dependencies, DNS or traffic steering, data integrity and operator runbooks behave as designed.

Decision rule: derive topology from business impact and tested recovery objectives. “Two regions” is not itself a recovery plan.

SCENARIO 03 / RELEASE SAFETYRolling, blue/green or canary?+

Rolling: progressively replaces instances and can be operationally simple, but mixed versions may coexist and compatibility must be maintained.

Blue/green: keeps two environments available for a controlled traffic switch; it can simplify rollback but duplicates capacity and still needs compatible data changes.

Canary: exposes a small cohort first and expands based on observed health; it needs meaningful telemetry, cohort control and clear abort thresholds.

Review before decision: blast radius, deployment duration, traffic distribution, database migration compatibility, session handling, observability coverage and who can stop/rollback.

Decision rule: choose a deployment strategy only when its rollback path and compatibility assumptions are tested, not merely documented.

SCENARIO 04 / INFRASTRUCTURE STATELocal Terraform state or remote backend?+

Local state: can be reasonable for an isolated personal experiment with one operator and disposable resources, provided the file is protected and backed up where needed.

Remote state: is the normal team pattern when multiple operators or automation need a shared, access-controlled state location and supported locking/concurrency controls.

Review before decision: backend access, encryption, state sensitivity, locking support, recovery/versioning, workspace boundaries, identity lifetime and break-glass ownership.

Failure test: verify concurrent operation behaviour and recovery from a deliberately interrupted workflow in a disposable environment. Never test state corruption against a valuable workspace.

Decision rule: state is sensitive operational data. Select a backend based on collaboration, protection and recovery requirements—not convenience alone.

LEARNING PROGRESSION / ENGINEERING SEQUENCE

Build capability one dependency at a time.

A dependency-led sequence, not a calendar or a claim of mastery. Each stage builds on the previous one and includes a practical readiness check; move forward when you can explain the concepts, reproduce the exercise and diagnose its failure modes.

  1. 01
    Understand systems

    Linux, process behaviour, networking, scripting, Git, HTTP, and software lifecycle fundamentals.

    Readiness checkCan isolate a failure by layer

    Given a local service that cannot be reached, trace the process, listener, route, DNS, TCP, TLS and HTTP path. Record the first failing boundary and the evidence that supports it.

    Evidence: a concise diagnostic runbook with commands, observations and a verified resolution.

  2. 02
    Automate and package

    Shell/Python automation, CI pipelines, tests, containers, registries, and secure artifact practices.

    Readiness checkCan automate a repeatable change

    Write a small script that validates inputs, handles errors, is safe to rerun and has tests. Build a container image with explicit inputs and verify the same artifact by digest through the delivery stages.

    Evidence: a repeatable workflow, test output and an artifact identity linked to its source revision.

  3. 03
    Provision and orchestrate

    Cloud networking, IAM, Terraform, configuration management, Kubernetes, and workload operations.

    Readiness checkCan plan and operate infrastructure safely

    Review an IaC plan for replacements and destructive changes, explain the state boundary, then inspect a Kubernetes workload’s scheduling, probes, resources, rollout and service endpoints.

    Evidence: a reviewed plan plus a workload diagnosis that distinguishes desired, scheduled, ready and available state.

  4. 04
    Reconcile and platform

    Helm, Kustomize, GitOps, developer platforms, environment promotion, and policy automation.

    Readiness checkCan explain desired-state reconciliation

    Trace a repository change into a rendered manifest and explain how the controller detects drift, syncs changes, handles pruning and supports rollback. Identify the repository and identity permissions that protect the path.

    Evidence: a tested promotion and rollback procedure in a disposable environment, with clear guardrails.

  5. 05
    Observe and improve

    Telemetry, SLOs, incident response, security controls, disaster recovery, and cost accountability.

    Readiness checkCan connect service signals to action

    Define an SLI with an explicit good-event rule and window. Use metrics, logs and traces to investigate a synthetic incident, then explain the recovery objective, security impact and cost trade-off.

    Evidence: an incident record with a user-impact signal, diagnosis, mitigation, follow-up and validated recovery assumption.

How to use the progression

Treat each checkpoint as evidence to produce, not a badge to claim. Keep a short record of the environment, expected result, test, failure injected, diagnosis, cleanup and remaining limitation. Revisit earlier stages when a later operational problem exposes a gap.
